# API — agent guide

ASP.NET Core 10, EF Core (Npgsql in production, SQLite locally and in tests), SignalR. Repo-wide rules are in `../CLAUDE.md`, and tests in `../tests/CLAUDE.md`. Run `dotnet run` here (port 5050, SQLite, demo data in Development).

## Glossary (entity names in `Entities/`)

- **Competition**: one event. `CreatedByUserId` is its owner; `SignupsLocked` closes entries; `IsArchived` marks archived events (`EventArchiveService`, `GET /api/competitions/{id}/archive`); `TermsText` is the organiser's optional terms shown beside the sign-up tick; `EnablePassportCheck` enables equine passport/flu checks in event tools; `DecFormConfig.UseRefereeCards` is the server setting (preserved through form save/reset); the current web visibility switch is still device-local until frontend wiring lands. There are no `YellowCardsEnabled` or `RedCardsEnabled` entity fields.
- **Section** (`CompetitionSection`): an age group in a competition, with a `Format` (Pairs, Teams, Individual), `UsesRaceFinals`, `HasFinal`, `CarryPointsIntoFinal`, `DoublePointsInFinal`, `PriceMinor` (pence), `MaxParticipants` and `FinalistCount`.
- **Session**: a timetable block with `Kind` (Race, Break, Briefing, Custom), `Status` (Upcoming, InArena, Finished), `LanesPerHeat`, `PlannedRaces` (A Final or session race list), `PlannedFinalRaces` (optional JSON per-final race lists keyed `"B"`, `"C"`, etc.), and provisional result confirmation timestamps (`ProvisionalUntil`, `OfficialConfirmedAt`). The **timetable** is sessions and heats ordered by `OrderIndex` and `ScheduledStart`. Organisers can shift uncompleted sessions (`POST .../sessions/shift-times`) or pause/resume an arena (`POST .../sessions/pause` and `resume`, tracked via `[paused:<ms>]` and `[shift:±N]` in `Session.Notes`). A pause can say why (`reason` `thunder` or `rain`, stored as `[pausefor:thunder]` beside `[paused:<ms>]`) and carry an `announcement` (posted with tag `weather` in the same request, so it works for every organiser, not just site admins); `resume` takes an `announcement` too, and `POST .../sessions/weather-notice` tells everyone without pausing. These back the organiser's weather alerts (`docs/plans/2026-10-27-weather-alerts.md`). `hold` reads a typed resume time as UK clock time.
- **Chat, announcements & message threads** (`ChatController`, `Services/SwearFilter.cs`): public announcements (`POST .../chat/announcement`), pin/unpin (`POST .../chat/{messageId}/pin`), heat-scoped missing-team ring calls (`POST /api/heats/{heatId}/call-missing-team`, auto-deleted when the heat starts/scores), and WhatsApp-style private message threads between signed-in users and organisers (`GET /api/competitions/{id}/chat/threads`, `GET/POST .../chat/threads/{userId}`). Chat text is swear-filtered on the server (`SwearFilter`: keeps the first letter, stars the rest).
- **Heat**: the teams racing together, with `HeatEntry` lanes and a `RaceRoundStage` (None, Qualifier, Final). **Race**: one game run within a heat, holding `Result` rows (placing, points, eliminated). **RaceTemplate**: a library game with rules and `DiagramJson` across 4 governing bodies (**EGUK**, **Pony Club**, **MGA**, **STRUK**), fetched per race via `GET /api/race-templates/by-name/{name}`; `IsBuiltIn` ones are refreshed at startup.
- **Team**: a club's entry in a section. **HC** (`IsHorsConcours`) teams race but are left out of standings and finals. **TeamSupporter**: a follower the trainer has approved.
- **Declaration form** (`DeclarationForm`): a team's riders (`RiderEntry`: reserve, `HorseName`, `PonyHeightHands`; captain and order are kept but no longer asked for). There's no pony entity. The form records `TrainerName`, the required terms tick (`TermsAcceptedAt`, `TermsAcceptedByUserId`), and equine flu vaccination certification (`PonyVaccinationConfirmed`, `FluLastShotOn`, `PassportVerifiedAt`, `PassportVerifiedByUserId`; `POST /api/declaration-forms` answers 400 without `AcceptTerms` or when `FluLastShotOn` is older than 6 months / in the future). `SavedRider` is a reusable roster entry. **Adaptive dec form** (`Services/DecForms/`): `Competition.DecFormConfigJson` (null = the standard form, name, date of birth, pony, height and bib) holds the organiser's setup (plus `PayoutClubId` pinned at competition creation), which `DecFormRules.Apply` enforces on submit: required means refused, an answer to a switched-off part is dropped and never stored, and a number outside a custom field's min or max is accepted but stored as a flag in `RiderEntry.FlagsJson` (not recomputed, so changing the rules never rewrites old forms). Weight, birth year/age group, passport, membership, emergency contact, medical notes and custom values are personal data about a child: `ToPublicDto` blanks every one, and only staff and the submitting trainer get them (`CanReadPrivate`). Never select them in stats, exports for the public or logs. **Bib**: `Team.BibDescription` is the one description a team gives on its dec form; `BibColour` stays on club, team or rider.
- **Signup** (`SectionSignup`): a paid entry. An admin marks payment received; no real money moves. On a **demo event** (`EventCommerceSettings.IsDemo`, the only mark; the review seeder sets it) the entrant pays through the fake provider instead: `POST /api/commerce/signups/{id}/demo-checkout` and `demo-refund` answer 403 on any other event. Demo mode cannot be turned on once an event has paid entries. Organiser totals and the committee report must read income from `RealIncome.ForCompetitionAsync`, which ignores demo events and test orders. Creating one needs `AcceptTerms` and the current `ConsentVersion` (`SignupTerms`); the tick, who, when and wording version are stored on it. A guest or individual entry made by a parent can carry the rider's name, date of birth and pony plus a parent/guardian and emergency contact (`SignupGuestDetails`, checked in `SignupController.ParseGuestDetails`; whole-team entries drop them). That is personal data about a child: it goes only in `SectionSignupExtendedDto.Guest` (staff list, the create reply) and `MySignupExtendedDto.Guest` (the entrant's own), never a public DTO, stats, logs or share card. Team formation names the rider from it (`RiderOf`).
- **Club payouts** (`ClubPayoutAccount`, `ClubPayoutsController`, `Services/Payouts/`): a mock of provider-hosted onboarding (Stripe Connect Express style), one per club, no money moves. `GET/PUT /api/clubs/{id}/payouts`, `PUT .../bank`, `POST .../finish` (sets Ready once everything is valid; any later edit drops it back to InProgress) are for that club's Manager or an admin (another club's manager gets 403). **Never persist, log, return or echo a full account number or IBAN**: they are validated in `PayoutRules` and only the sort code, last four digits and IBAN country are stored; the controller injects no logger on purpose. The responsible person's date of birth is returned only by those endpoints. `GET .../summary` and `CompetitionDetail.PayoutsTo` (the organiser's club) are the public, no-personal-data summary. Format rules are mirrored in `web/src/lib/payouts.ts`.
- **Season**: a points league over competition sections (`SeasonRound`, `SeasonPlacePoints`, `BestResultsToCount`). Results are published as versioned snapshots (`SeasonRoundPublication`).
- **Operations**: rulebook, score state and audit (`RaceScoreState`, `RaceScoreEvent`), draw, readiness checks, equipment acknowledgements, and volunteer/emergency coordination (`VolunteerAndEmergencyController`: volunteer shifts, claims, attendance check-in, session duty assignments, and emergency contact lookup). **Entry status**: `Team.EntryStatus` (Active, Withdrawn, NoShow) with reasons in `TeamStatusEvent`; `DrawChange` logs each applied draw and re-draw; `RiderSwapEvent` audits reserve swaps. **Event tools**: clone (set-up only: `CompetitionSetup` carries sections, timetable plan, race lists, hatbands, dec form and payment details, never teams, heats, results, entries or payments), CSV team import, printable pack, and JSON archive export (`EventArchiveService`). **Starting point** (`StartingPoint`, `StartingPointsController`): a saved `CompetitionSetup` under a name, private to its owner (admins see all), used to create competitions. Readiness also reports `FlaggedDecForms` (riders with flags per team, counts only) and `RaceListsToChoose` (race sessions with no races chosen); neither changes `IsReady`.
- **Sponsor** (`Sponsor`, `SponsorExposure`): a competition's sponsor with a tier, an https link, a logo (png/jpeg/webp up to 200 KB, stored in the row and served by `SponsorsController`) and `ShowOn`, a set of `SponsorPlacement` flags. `SponsorExposure` holds daily counters per sponsor and place (views, and seconds on video) with nothing that identifies a viewer.
- **Shop** (`ShopPost`, `ShopComment`, `ShopReport`): marketplace posts. **Commerce**: event shops with listings and orders. A catalogue item can have seller-defined options (`CatalogueItemOption`, usually sizes, each with optional stock); an order line for such an item must name one (`CreateEventOrderLineRequest.OptionId`), stores `OptionLabel` as a snapshot, and reserves/releases that option's stock (`ReservedOptionStockQuantity`) with the same guarded decrement and version bump as the item's own stock (`CommerceOrderService.ReserveAsync`). Nothing guesses options from an item's title.
- **Scorer link** (`ScorerLink`): a no-account way to score one competition (its arena name is now just a label). Only a SHA-256 hash of the token is stored; the token is shown once on creation. Made, listed and revoked by anyone `[CompetitionAccess]` lets in, through `ScorerLinksController`.
- **Email** (`Services/Email/`): `IEmailSender` (`LoggingEmailSender` unless `Email:Enabled`, `Email:ApiKey` and `Email:From` are all set, then `ResendEmailSender`). `SignupConfirmationService` sends the one entry confirmation inline from `SignupController.Create`; the result goes on `SectionSignup.ConfirmationEmailStatus`. `EmailOptIn` is the consent list for new-competition emails (unticked box, hashed unsubscribe token, site-admin CSV export). **Custom emails** (`CustomEmailService`, `CustomEmailsController`): admins write blocks (text, picture, button, competition card, footer) to an audience (news list, trainers, organisers and admins, admins only). A text block can link words (`Links`: https address, or an event's page resolved to its https URL on the site), a picture can link somewhere, and the one footer block holds optional text and picture (blank text means the usual line; the news list always gets an unsubscribe link). The emails are plain: no banner, buttons or cards of ours. All of this lives in the `BlocksJson` column, so it needed no migration. The admin page is `web/src/pages/admin/EmailPage.tsx` (`/admin/email`). `POST /api/admin/custom-emails` freezes the email and its recipients, then `send-batch` is called until `remaining` is 0 (claim, send with an idempotency key, delete the row); see `docs/decisions.md`, 25 Oct. Later emails to the news list use signed unsubscribe links (`EmailUnsubscribeTokens`), because the stored token hash can't be turned back into a link. **Entries-open digest** (`EntriesDigestService`, `EntriesOpenRule`, `EntriesDigestEmail`; tables `EntriesDigestRuns`, `EntriesDigestCompetitions`, `EntriesDigestRecipients`; `EntriesDigestController` at `/api/admin/entries-digest`): `NotificationScheduler.DigestTickAsync` calls `TickAsync` every minute; between 18:00 and 22:59 UK time (`UkTime`, Europe/London) it claims the day by inserting the run (unique `RunDate`), its competitions (primary key = competition id, so announced once ever) and one recipient row per opt-in address in a single `SaveChanges`; a lost race means nothing was written. Recipients hold the opt-in id, not an address; the address is read at send time and re-checked against unsubscribes. Batches are claimed with a token, sent with the idempotency key `entries-digest-{run}-{optIn}`, failed ones retried after 15 minutes up to 3 times, runs older than 2 days closed. The first ever tick is a baseline that announces nothing. Email off (or no `Email:SiteUrl`) means no run is claimed and nothing is marked announced. Order within an email: nearest first from `LocationInference` (history of entries, training and supporting; never stored), else by date. No Vercel cron is configured (see the plan), so the evening send needs an awake instance; the admin's Send now covers a gap.
- **Roles** (`Auth/Roles.cs`): Admin, MasterAdmin (held as well as Admin; locks and unlocks Admin and organiser accounts; never grantable through the API except with the master admin key: `POST /api/auth/master-admin`, checked against `MasterAdmin:KeyHash`, the SHA-256 hex of a secret only its owner holds; unset means 404), Trainer, TrainerRequest and ManagerRequest (signed up, awaiting approval), Manager, Member, Rider.
- **Account access** (`Services/Accounts/`): `AppUser.LockedAt` (admins lock organisers, a master admin locks Admins) and `BlockedAt`/`BlockReason` (admins) stop sign-in and kill existing tokens through `LiveAccounts`. Blocking adds the account's networks to `IpBlocks` as hashes (`BlockedAccountUserId`), recorded at sign-in in `AccountIps`; always test a visitor with `IpBlocking.IsIpBlockedAsync`, never `IpBlocks` directly. `AccountInvite` is an emailed one-time link (token hash only) that makes an organiser or site admin. The block reason is admin-only: keep it out of every other DTO. "Steward" and "spectator" are product words with no role behind them.

## Recipes

- **Endpoint:** attribute-routed action with `[Authorize(Roles = Roles.Organiser)]` and, for per-competition writes, `[CompetitionAccess("competitionId")]`. The name must match an `int` action argument; use `CompetitionResource.Signup` when the id is a signup id. It's method-only, returns 404 (not 403) to non-owners, and admins pass. Reject bad input with `BadRequest(new { message = "..." })` (newer code uses `ValidationProblem` or `Problem`) and use `[Range]` on DTO records. Every non-GET `/api` call is already rate-limited (60/min per user or IP); add `[EnableRateLimiting("auth")]` only to sign-in-style endpoints. Copy `Controllers/TeamsController.cs`.
- **Field through the stack** (see `Team.IsHorsConcours`): entity, then the request and response records in `Dtos/ApiDtos.cs` (positional, so order matters), then **every** `ToDto…` overload in `Services/Mappings.cs`, then controller create and update (nullable on update means "leave unchanged"), then `web/src/types.ts`, then the schema steps below.
- **Schema:** `dotnet ef migrations add <Name>` (design time uses Npgsql). Then `dotnet ef migrations script <previous> <Name> --idempotent -o Data/Migrations/Scripts/<timestamp>_<Name>.sql`, matching the migration's file name. Then add the SQLite guard: `CREATE TABLE IF NOT EXISTS` or `EnsureColumnAsync(db, table, column, "INTEGER NOT NULL DEFAULT 0")` in `DbInitializer.EnsureSqliteSchemaAsync`, or in the area's `Services/{Operations,Commerce,Seasons}/*SqliteSchema.cs`. Use SQLite types (`INTEGER` for bool and enum, `TEXT` for DateTime and Guid). Add a schema test. Run `npm run db:migrate` (root, EF `MigrateAsync`) on Neon **before** the API deploys: on Postgres the API won't start with a pending migration.
- **Public read (crawlers, calendar apps):** anonymous `GET` with `[AllowAnonymous] [PublicRead] [EnableRateLimiting("public-read")]` (`Security/PublicReadAttribute.cs`: refuses `IpBlocks` addresses; the policy limits per IP, `RateLimits:PublicReadsPerMinute`, default 120). Return only facts the public page already shows (`ShareController` is the model). Never put a link, host or user input into a response that shared caches may keep.
- **Sponsor placement** (a new place a sponsor can appear): add a value to `SponsorPlacement` in `Entities/Sponsor.cs` (the next power of two; `SponsorPlacements.All` and the validation follow by themselves), then do the web steps in `web/CLAUDE.md` ("Sponsor placement"). No migration is needed, because `ShowOn` is a plain integer. A web test fails if the enum and the web registry differ.
- **Live event:** add a method to `ILiveBroadcaster`, implement it in `LiveBroadcaster` (`Hubs/LiveHub.cs`), call it after `SaveChanges`. Groups: `comp:{id}` (everyone joined), `comp:{id}:admins` (Admins only), or `Clients.User(id)`. Register it in `web/src/live/useLiveHub.ts` with the same name. Staff-only data needs **both** a restricted broadcast and a filter on the REST read (see `ChatController.Recent` and `Post`).
- **Demo data:** `DbInitializer.SeedDemoDataAsync` runs in Development only (and not when `Database:SeedDemoData` is false). The larger review set (eight "Demo …" events) comes from `ReviewCompetitionSeeder` through `npm run db:seed-review`, never at startup. It skips names that already exist, so it can't refresh old data. `npm run db:reseed-review` (`--reseed-review-competitions`) can: `RemoveReviewCompetitionsAsync` deletes an event only if its name is one of the eight seeder names **and** `EventCommerceSettings.IsDemo` is true, then seeds them again. It removes each event's whole graph by hand in one transaction (not relying on DB cascades), so **a new table keyed by competition, section, team, session, heat, race, signup or order must be added to it**, with a case in `ReviewSeedFreshTests`. Same-named events without the mark are reported and left alone (and not given the mark); a demo event in a season stops the run. Both commands pass the real time, so today's event (offset 0) is timed from it: the running session started about 30 minutes ago, the finished one ran before, and each arena's upcoming sessions follow. Without a time (`nowUtc` null) it stays fixed at 09:00 in 80-minute steps. Run them against local SQLite or deliberately against Neon, never by accident. **History seed** (`HistorySeeder`, `npm run db:seed-history`, `--seed-history`): a separate, idempotent back catalogue (12 clubs, ~180 riders, 8 finished past events with every race scored plus one upcoming event with an event shop, one season, 15 shop posts, 10 catalogue items, no images). It owns the `history-seed-*` accounts (no password, locked), finds its events by stable name plus the demo mark, and removes only those (through `ReviewCompetitionSeeder.DeleteCompetitionGraphAsync`, so a new competition-keyed table goes in that one place); a same-named unmarked event stops the run. It runs on top of `db:reseed-review` without clashing: the review reseed only touches the eight Demo names.
- **Real event from a file** (`Services/EventTools/CompetitionFileImport.cs`, `npm run db:import-competition -- /path/event.json [--dry-run]`, `--import-competition`): adds one unscored, non-demo event (pairs or individuals) from a JSON file of sections, heats with riders per lane, race lists and planned finals sessions (drawn on the day with Create finals into that session). Riders are children, so the file stays outside git (a `*.local` folder is ignored) and tests use made-up names. It refuses an event of the same name within a day, an unknown owner email, or a bad file, and saves in one go.

## Invariants

- **Scoring goes through `ScoringService`**; never write `Result` rows from a controller. Team-card updates change current team metadata only and preserve historical result notes. `Team.BibDescription` is an EF concurrency token so stale ordinary edits cannot erase organiser-owned card metadata; return 409 when a conflicting edit needs reloading.
  - Placing points = largest heat size in the session − place + 1. Eliminated = 0.
  - Qualifier heats in race finals give 1 per finisher.
  - A referee note can carry one points directive: `[pts:N]` sets the race points and `[adj:±N]` moves the placing points (never stored points, so a re-save can't apply it twice). It wins over everything but a sit-out.
  - Points are `double`, whole or half only (`PointValues` validates any value written, e.g. `FinishingPlaceDto.Points`; a dead heat can give 2.5). Totals, standings and stats are `double`; format with `PointValues.Format` in text, and `formatPoints` on the web. Season place-award rules stay `int`.
  - Each save replaces a race's results and bumps `RaceScoreState.Revision`. Corrections need a `reason`; signed-off races refuse with 409.
  - Every write carries a `RequestId`, replayed idempotently (that's how the web outbox retries safely). Runs in a Serializable transaction.
- **Day-of endpoints (scoring, sessions, finals, timetable) are for the competition's staff:** `[Authorize(Policy = CompetitionStaff.Policy)]` plus `[CompetitionAccess(...)]` (by `competitionId`, or `raceId`/`heatId` with `CompetitionResource.Race`/`Heat`). Staff are admins, the owning Trainer and the competition's competition admins (`CompetitionCollaborators`, added through `/api/competitions/{id}/team`), who can do everything the owner can for that event; check access with `CompetitionManagers` rather than comparing `CreatedByUserId`. Deletes, chat moderation and global data stay `Roles.Admin` (`docs/decisions.md`, 22 Oct). Any request field naming teams must be checked against the competition (`SessionsController.TeamsBelongAsync`).
- **Withdrawn and no-show teams** (`Services/Operations/TeamEntryService`): leaving removes the team from every *unscored* heat (`HeatProtection.IsProtected` says which are protected: results, complete, started, signed off, finished session) and leaves scored heats and their points alone. The reason is organiser-only (`TeamStatusEvent`); public DTOs expose just `IsWithdrawn`. Out teams are left out of the section draw, heat generation, finals seeding and readiness, and can't be hand-placed in a heat. They stay in standings with their points (`StandingRow.Withdrawn`). The re-draw (`WithdrawalRedrawService`) only moves teams between unscored heats, applies atomically against a fingerprint, is idempotent per `RequestId`, and broadcasts `sessionUpdated`.
- **Final switches** (`CompetitionSection.HasFinal`, `CarryPointsIntoFinal`, `DoublePointsInFinal`; standard format only, ignored for heat-heat-final): `SectionScoring` is the one place that totals a finalist, so standings, printed results and season publication agree; doubling happens in `ScoringService` when a final race is saved. See `docs/decisions.md`, 25 Oct.
- **Standings and finals seeding** exclude HC teams and sort by total points; teams level on points go through `TieBreaker` (`Services/TieBreaker.cs`): the organiser's `FinalsTieOrder` when one is set for the whole tie at its current total, otherwise the section's `TieBreakRule` (countback on places by default, or last race; run-off and manual wait for the organiser and fall back to countback). `FinalsBoundary` reports every tied finals cut and whether it is settled; `PUT /finals/tie-order` sets an order. Race finals interleave the top N from Q1 and Q2 into the Final, skipping withdrawn and HC teams. `FinalistCount` is stored but not yet used by server logic.
- **Wire format:** enums are numbers (no string converter). On Postgres every `DateTime` is UTC except birth dates, which are calendar dates (`AppDbContext`).
- **ETags:** `JsonEtagMiddleware` hashes every `GET /api/*` body for 304s and sends `private, no-cache`. Keep it that way, because many responses vary by user.
- **Scorer links** (`ScorerController`, `Auth/ScorerLinkAccess.cs`): `[ScorerLinkAccess]` reads `X-Scorer-Token` (missing 401, unknown or malformed 404, revoked or expired 410, too many unknown tokens from one address 429). The token goes in the page fragment (`/score#t=…&k=mg-scorer-v1` or `?scope=mg-scorer-v1`), never a path, and is never logged or returned again. A link is scoped to its competition and optionally to a single `SessionId` or `HeatId` (`20261024203315_AddScorerLinkScope`; out-of-scope sessions/heats/races return 403/404) and can read the competition's timetable (filtered to its scope) and enter or replace scores, including referee notes, so a link can also set points with a note directive: no clock, sign-off, reopen, timetable, teams, entries, chat or private reads. Scores go through `ScoringService` with an `actorLabel` ("Scorer link: {label}") stored on `RaceScoreEvent.ActorLabel`. Default expiry is the end of the day after the competition's end date; a link can be shorter, never longer. Scorer saves have their own per-IP write limit (`RateLimits:ScorerWritesPerMinute`, 240) and unknown tokens a failure budget (`RateLimits:ScorerFailuresPerMinute`, 20, per instance). A new endpoint here must call `InScopeAsync` first. `ScorerLinkTests` walks every authorised endpoint with the token and fails if any accepts it.
- **Email:** a send never fails or rolls back a sign-up (the sender returns a status and never throws), and it runs inline with a short timeout because the API scales to zero (no background queue). Logs hold a masked address (`EmailAddresses.Mask`) and never a body, the full address or the key. Addresses appear only in staff-only responses (`GET .../signups`) and the admin CSV; never add one to a public DTO. A retried submit is recognised by `SectionSignup.ClientRequestId` and gets the first entry back. Opt-in state is not in any DTO. Changing the opt-in sentence means bumping `EmailOptInWording.Version` and `web/src/lib/emailOptIn.ts` together.
- **Sponsors:** managing them is `CompetitionStaff` + `[CompetitionAccess("competitionId")]`; the list, the logo and `POST …/sponsors/exposures` are anonymous. The public list returns only sponsors that are enabled and inside their dates, never organiser fields. Logos are checked by magic bytes against the declared type (`Services/Sponsors/SponsorLogos.cs`), never SVG, and links must be https. Exposure reports are limited per IP by the `sponsor-exposure` policy (`RateLimits:SponsorExposurePerMinute`, 12), take at most 40 items, and ignore sponsors from other competitions. `StreamOverlay.SponsorMode` (Auto in breaks, On, Off) is the producer's switch; "skip" is relayed to viewers as `sponsorControl` and stores nothing.
- **Streaming:** only the API talks to Cloudflare (`Streaming:Cloudflare:*`). DTOs never include SFU session ids or tokens, and nothing logs bodies, tokens or SDP. Streaming is off (writes return 503) unless both AppId and AppToken are set. Hub methods (`WatchStream`, `AnswerStream`) allow anonymous callers, so a new hub method must make its own checks.
- **Startup checks** (`Security/SecurityConfiguration.cs`): outside Development, `Jwt:Key` must be at least 32 bytes and not come from appsettings. `Admin:Key` is optional but at least 20 bytes if set (without it, there's no shared admin). `Database:SeedDemoData=true` throws.
- **Calendar feeds:** `GET /api/calendar/teams/{teamId}/{token}.ics` is the only credential a calendar app can send, so the token is 32 random bytes, only its SHA-256 is stored (`Team.CalendarFeedTokenHash`), a wrong token, wrong team and a switched-off feed all give the same 404, and regenerating replaces the hash. The team's trainer and anyone `CompetitionManagers` lets run the competition manage it. Heat events keep a stable UID (`heat-{id}-team-{id}@mg-app`); `CalendarHeatVersion` raises `SEQUENCE` and `LAST-MODIFIED` when a heat's published details change. `TimetableTimes` mirrors `web/src/lib/time.ts` (`computeTimings`): change both together. The feed lists only what the public timetable shows, never riders.
- **Statistics hub** (`StatsController`, `Services/Stats/`): anonymous search and headline numbers, plus a team profile's per-game figures (team kind only: riders and ponies need sign-in for them); entries and partnerships only for a signed-in caller, decided in `StatsService` (never trust the web to hide them). Riders and ponies match by normalised name (`StatsNames`) from each team's latest **locked** declaration form; only finished, non-demo competitions count; places come from `StandingsService.RowsAsync`. A rider with `UseInitialOnly` is matched on `RiderNames.Display(..., viewerSeesFullNames: User.IsInRole(Admin))`, so their surname finds nothing for anyone else. Never select `RefereeNote`. Limited by the `stats` policy (`RateLimits:StatsPerMinute`, 60, per user or IP).
- **Client IP** comes from `Security/ProxyClientIpMiddleware` (trusted proxy plus `Security:ProxyKey`) before rate limits, IP blocks and chat. Don't read `X-Forwarded-For` yourself. The same middleware reads the connection's rough place (`X-MG-Client-Lat/Lon`, one decimal place) **only with a valid key**, re-validates and re-rounds it, puts it in `HttpContext.Items` (`VisitorGeo.Get`) for that request, and always strips the headers. It is only used by `GET /api/competitions/picker/near-you` (`private, no-store`, outside the public caches); never store it, log it, or return it (the answer holds whole-mile distances only). The plain `/picker` must stay identical for every viewer.
- Headers in `Security/SecurityHeadersMiddleware.cs` must match `web/vercel.json`. Paths starting `/embed/` (the results widget) get `EmbedHeaders` instead: `frame-ancestors https:`, no `X-Frame-Options`. Nothing else may be framed. Change both header sets and both Vercel rules together; `SecurityTests` checks the pairs and the path split.
- Endpoints or controllers marked `// Unused in web UI yet — reserved for iOS / upcoming wiring` are intentionally retained for the native iOS app and upcoming UI wiring.
