# Project decisions

## 2026-10-24: Entrant declaration access needs trusted team formation
- Why: riders need to complete declarations for their own pairs and individual entries, but public supporter codes and matching names do not prove that someone is a team entrant.
- Rule: the existing coach, club manager and organiser permissions remain. An entrant also needs an active Pending or Paid signup, an explicit link to the same section's team, no withdrawal, and `SignupMatchmaking.DeclarationAccessGranted`. Only organiser team formation and mutually accepted pair requests set that grant. Typing a team name or a public supporter code never grants declaration access.
- Old runtime matchmaking rows default to no grant when adopted. Their names or existing team links are not used to infer permission. Authorised organisers can form their teams; existing staff permissions still work.
- Private reads, draft visibility, submission and deletion use the same trusted-entry check. The web filters its team choices using the grant returned by the API; server checks remain authoritative.
- Supersedes: the coach-only restriction in the 2026-10-22 declaration decision, solely for these trusted entrants.
- Files: `api/Controllers/{Signup,DeclarationForms}Controller.cs`, `api/Entities/EntryExtensions.cs`, `api/Data/AppDbContext.cs`, `web/src/pages/competition/DeclarationsTab.tsx`.

## 2026-10-23: Sign-up passwords and emails are checked, and new accounts confirm their email
- Why: a walkthrough found the password rules weren't shown while typing, the error said "non-alphanumeric", and nothing checked an email was real, which we'll need once emails are used properly.
- Passwords: the rules are unchanged (8 or more characters, a digit, a lowercase letter, a special character, no capital). The sign-up page shows a live checklist (`PasswordChecklist`) driven by `web/src/lib/passwordRules.ts`; a test there reads `api/Program.cs` and a test in `EmailAccountTests` reads the Identity options, so neither side can drift. Error codes map to the same words on the API (`PasswordRules.Friendly`) and the web; "non-alphanumeric" is never shown. Sign-up is the only place a password is set today.
- Addresses: strict shape check on both sides (`EmailValidation` / `emailCheck.ts`), a short built-in list of disposable domains, and a mail-domain check on the API (`IEmailDomainChecker`, DnsClient: MX, then A/AAAA, null MX counts as no mail). A DNS timeout or server failure fails open and is logged with the domain only. The web suggests fixes for common typos (gmial.com and so on). Made-up usernames (no `@`) still work as before and are treated as confirmed.
- Confirmation: new sign-ups with a real address start with `EmailConfirmed = false` and get one email (`AccountEmailService`, same sender and `Email:SiteUrl` as entry confirmations). The link is `/confirm-email?userId=...&token=...`; `POST /api/auth/confirm-email` is anonymous and answers every bad link the same way. `POST /api/auth/resend-confirmation` is signed-in and limited to 3 a minute per person (`RateLimits:EmailResendPerMinute`). Sign-in is not blocked; `emailConfirmed` is on the user profile for later. Existing accounts stay confirmed (no data change, no schema change).
- Tokens: not Identity's token provider, because it depends on Data Protection keys and this API has no shared key store (scale-to-zero instances would reject each other's links). They are HMAC-signed with a key derived from `Jwt:Key`, expire after 3 days, and are bound to the user id, address and security stamp. Confirming twice is harmless. Tokens and full addresses are never logged.
- Files: `api/Services/Email/AccountEmail.cs`, `api/Controllers/AuthController.cs`, `web/src/components/{PasswordChecklist,EmailConfirmBanner}.tsx`, `web/src/pages/{SignUpPage,ConfirmEmailPage}.tsx`, `tests/MountedGames.Api.Tests/Auth/EmailAccountTests.cs`.

## 2026-10-22: Embeddable results widget
- Why: clubs and associations want live standings, results or the timetable on their own site (`docs/competitive-gaps.md` point 9). A pasted iframe snippet does it; a public JSON feed is not included.
- Routes: `/embed/competitions/:id/{standings,results,timetable}` and `/embed/seasons/:seasonId/standings`. Options in the address: `accent` (3 or 6 hex digits, strictly validated, nudged for contrast), `theme=light|dark`, `section=<age group id>`. Nothing else is read; no CSS or URLs from the query string.
- Framing: only paths starting `/embed/` may be framed, with `frame-ancestors https:` (any https page) and no `X-Frame-Options`. Every other path keeps `frame-ancestors 'none'` and `X-Frame-Options: DENY`. Why any https origin: the snippet is meant for any club's site, and the widget shows only public data. Restricting it to named domains would need a per-competition allow-list stored in the database and a header written per request by the API; Vercel's static header rules can't do that, so the web project would have to stop serving those pages itself. Not built; add it if a club ever needs it.
- Headers are defined twice (`SecurityHeadersMiddleware` and `web/vercel.json`). Vercel has two rules, `/((?!embed/).*)` and `/embed/(.*)`, so exactly one applies to a path (a test checks this). The embed set also uses `Cross-Origin-Resource-Policy: cross-origin` and a Permissions-Policy without camera or microphone. The CSP gains `frame-src 'self'` everywhere so the organiser's preview can load; other pages still refuse to be framed, so only `/embed/` pages can appear there.
- Isolation: the widget is its own small app (`EmbedApp`), not under the sign-in, theme, current-competition or offline providers. `main.tsx` skips the service worker, push and score outbox on `/embed/` paths. It fetches with `credentials: 'omit'`, no token, and an `X-MG-Embed` header; the service worker leaves those requests alone and its navigation fallback skips `/embed/`.
- Data: public endpoints only (`/competitions/:id`, `/standings`, `/seasons/:id`, `/seasons/:id/standings`). Team names, places, points and times; no riders, trainers, entrants or contact details. Qualifier heats stay hidden as on the public timetable. Polling, not the live hub, because a widget may sit on many club pages: 30 s while a session is on, 3 minutes otherwise, 1 and 5 minutes after failures, paused while hidden or offline. Unchanged answers are 304s.
- Organiser side: an "Embed on your website" card on the competition Details tab (anyone who `canOrganise`: admins, the owner, competition admins) and the season Settings tab. Fixed height with scrolling; no resize script.
- Rejected: a public JSON feed (decided out of scope); a resize script (a fixed height needs nothing on the club's page); reusing `TimetableBoard` and `ToplistView` (they need the app's providers and local storage, and another PR is redesigning them).
- Files: `api/Security/SecurityHeadersMiddleware.cs`, `web/vercel.json`, `web/src/pages/embed/`, `web/src/lib/embed.ts`, `web/src/hooks/useEmbedResource.ts`, `web/src/pages/competition/EmbedCard.tsx`, `web/src/offline/cachePolicy.ts`.

- Rejected: a new "isDemo" column on competitions (a second mark to keep in step); card-style inputs that accept test numbers (the page should never look like it collects card details).
- Not changed: the shop checkout still uses the older card-style demo form (`DemoPaymentFlow`); its API answers 409 rather than 403 on a real event.

## 2026-10-22: Withdrawals, no-shows, rider swaps and the re-draw
- Why: teams scratch and riders get swapped on the day, and the draw didn't react (`docs/competitive-gaps.md`, point 5). Decided the same day: the organiser marks a team out and swaps a rider; the app previews a re-draw of unscored heats and applies it only when confirmed. Trainer-side requests are not included.
- Team status: `Team.EntryStatus` (Active, Withdrawn, NoShow). The reason, actor and time live in `TeamStatusEvent`, organiser-only, never on the team row or any public DTO. Public DTOs carry only `isWithdrawn`.
- Going out removes the team from every unscored heat at once (so the public timetable, followed-team views and scoring see the remaining teams) and remembers its lanes. "Unscored" means no race in the heat has results, is complete, started, finished or signed off, the heat isn't started or finished, and its session isn't finished (`HeatProtection`). Scored and signed-off heats keep the team and its points; nothing is rewritten and no `Result` row is touched.
- Reversible until a draw is applied: reinstating puts the team back in the heats it left. Once a section draw or a re-draw has been applied for its section since, it is refused with a pointer to the timetable editor (`DrawChange` records every applied draw).
- Standings: a withdrawn team stays in the standings with its scored points and a `withdrawn` flag; HC rules are unchanged. Finals seeding (`POST /finals`, the finals boundary, populate-from-standings and populating a race final) leaves withdrawn teams out, so a team that cannot ride never takes a finalist place. Season standings are untouched (confirmed event results stand). Ambiguity for the owner: the toplist cut-off line still counts a withdrawn team's row, so the visible line can sit one place lower than the real finalist count.
- Re-draw: `GET /sections/{id}/redraw/preview`, `POST /sections/{id}/redraw/apply`. It works only on the unscored heats of each race session in the section (finals sessions and race-finals rounds are skipped), keeps teams where they are, closes lanes up, and moves the fewest teams: a heat that would hold fewer than two teams is merged away, sizes are balanced to within one, and the session's lane limit is respected when set. Teams that must move go where they have met the fewest of the heat's teams (the existing draw's opponent rule), with a stable hash as the tie-break. Same timetable, same answer. This is a cut-down use of the existing draw idea rather than a full reshuffle, so riders already told their heat keep it.
- Apply is one Serializable transaction guarded by the preview's fingerprint and a client request id (unique per competition in `DrawChange`): a stale preview gives 409, a retry of the same request returns the stored answer and changes nothing, a failed write rolls everything back. After the commit each changed session is broadcast as `sessionUpdated`, so phones and followed-team notifications recompute. The slip notification is client-side from heat times, so a re-draw that moves times by 15 minutes or more triggers it as before.
- Rider swap: `POST /competitions/{id}/declaration-forms/{formId}/swap`. The reserve takes the seat (and the captain badge), the rider goes to the reserves. Only the team's current declaration. Every declaration is locked on submit, so a swap always needs the explicit override and a reason. `RiderSwapEvent` keeps before/after, actor, time, reason and whether the lock was overridden. The trainer's own declaration flow is not widened.
- Also: withdrawn teams can't be added to heats by hand (409), are skipped when heats are generated, are left out of the section draw, and stop appearing in readiness (missing or incomplete declarations).
- Rejected: deleting the team's `HeatEntry` rows lazily at apply time (the public timetable would keep showing a team that has gone); a full reshuffle of every unscored heat (moves teams who were told their heat); writing withdrawal data onto `Team` (leaks through DTOs).
- Files: `api/Services/Operations/{HeatProtection,TeamEntryService,WithdrawalRedrawService,RiderSwapService}.cs`, `api/Controllers/WithdrawalsController.cs`, `api/Entities/Operations/{TeamStatusEvent,DrawChange,RiderSwapEvent}.cs`, migration `AddWithdrawalsAndSwaps`, `web/src/pages/operations/{EntriesPanel,RedrawPreviewView,RiderSwapSheet}.tsx`.

## 2026-10-22: One entry confirmation email, and an opt-in list for competition alerts
- Why: no email went out at all, and many parents won't get iOS push. The owner decided on one email, the entry confirmation, to the adult who signed up (never a rider), and competition-open alerts only for people who opt in. Schedule-change emails, results summaries and organiser broadcasts stay out.
- Sending: `IEmailSender` with two implementations. `LoggingEmailSender` is used unless `Email:Enabled`, `Email:ApiKey` and `Email:From` are all set (so always in Development and Testing); it sends nothing and logs a masked address only. `ResendEmailSender` posts to Resend's REST API once, with a 5 second default timeout (`Email:TimeoutSeconds`) and an `Idempotency-Key`. No retries and no background queue, because the API scales to zero on Vercel. A missing or half-set `Email:*` never stops startup or a sign-up.
- Sign-up: a new optional `ContactEmail` (validated, lower-cased, 254 characters). `ContactInfo` stays for a phone number. The confirmation (event, date, place, class, fee, the organiser's own payment instructions, a link to the competition page) goes inline after the entry is saved. Its outcome (sent, failed, not sent because email is off, and when) is stored on the signup and shown to staff. A failure never fails or rolls back the entry.
- Retries: the form sends a `RequestId`; the same person retrying the same section gets the first entry back, with no second entry and no second email (unique index on section, user and request id). A different request id is a different entry, as before.
- Opt-in: an unticked box on the form. Ticking it needs an address and the current wording version, and stores an `EmailOptIn` row in the same save as the entry: address, time, wording version, source, SHA-256 of a random unsubscribe token, unsubscribed time. An address already on the list gets no second row. The raw token exists only in the confirmation email sent at opt-in, so a future marketing sender must either issue fresh tokens or use the mailing tool's own unsubscribe. Unsubscribing (`POST /api/email/unsubscribe`, no sign-in, linked from `/unsubscribe?token=...`) ends every active consent for that address and answers identically for real, used and made-up tokens. Rows are kept as the record of consent and its withdrawal. Nothing is sent from the list in this change.
- Visibility: addresses appear only in the staff-only signup list and the site-admin CSV (`GET /api/admin/email-opt-ins.csv`, one row per active address). Staff see whether the confirmation went; nobody but a site admin sees opt-in state. Deleting an account clears the signup's `ContactEmail`; opt-in rows aren't tied to an account, so they stay until the person unsubscribes (or an admin removes the row).
- Rejected: Omnisend for the confirmation (not checked; the owner may use it for the alerts); a background send queue (the API can sleep before it runs); a pre-ticked box or opting people in because they gave an address (PECR/GDPR); storing the raw unsubscribe token (it would let a database leak unsubscribe or re-subscribe people).
- Privacy text to update (not changed here): the sign-up record now holds an optional email address; the confirmation email is sent through an outside email service (Resend) that sees the address and message; people on the opt-in list are held until they unsubscribe, with the date and wording they agreed to.
- Files: `api/Services/Email/`, `api/Controllers/SignupController.cs`, `api/Controllers/EmailOptInsController.cs`, `api/Entities/EmailOptIn.cs`, `web/src/components/EntryEmailFields.tsx`, `web/src/pages/UnsubscribePage.tsx`, `web/src/pages/admin/EmailOptInExportSection.tsx`, `tests/MountedGames.Api.Tests/Signups/EntryEmailTests.cs`.

## 2026-10-22: Deleting your own account
- Why: people must be able to remove themselves, and the privacy page promises it. `DELETE /api/auth/me` with the current password in the body does it (the same lockout as sign-in applies to wrong guesses).
- Refused: the shared admin account and any account with no password (admin-key sessions), with a message to ask an administrator; the last account in the Admin role.
- Rule: private data goes, event history stays with the person removed, ownership links are cleared. Each step is explicit in `AccountDeletionService`, not left to foreign-key cascades.
  - Deleted: trainer notes, push subscriptions, overlay looks, team supporter requests, competition team memberships, the saved rider roster (other people's children; declarations already made keep their own copy), private marketplace messages they wrote, sign-in roles/claims/logins/tokens.
  - Anonymised, kept: chat messages, marketplace posts, comments and reports (author link cleared, name becomes "Deleted user", IP address and post contact details cleared); declaration forms (`SubmittedByUserId` cleared); section signups (a payment record: account link and contact details cleared, the payer's name stays); private messages sent to them stay for their author, no longer addressed to anyone.
  - Ownership cleared: `Competition.CreatedByUserId` and `Team.TrainerUserId` become null. The competition or team carries on, an admin can run it, and a team shows as unclaimed.
  - Left as they are: audit columns that hold a bare user id with no foreign key (scoring audit, rulebook and overlay "updated by", `CompetitionCollaborator.AddedByUserId`, IP block creator, stream starter). With the account gone the id points at nobody.
  - Kept as an emptied shell (no migration): seasons, team profiles, season publications, event team links, catalogue items and event orders reference the account with non-nullable restricted keys. If the account owns any, the row stays but is anonymised in place: email and name replaced, phone and password cleared, roles removed, locked out for good, and catalogue items switched off. Everything else above still happens. The username is freed for reuse.
- Sessions end with the account: `LiveAccounts` turns away a token whose account is gone or emptied (checked on each request, cached for 60 seconds, so another API instance may accept it for up to a minute).
- Rejected: always anonymising in place (leaves a row for every leaver); cascading deletes through seasons and orders (would erase published results and payment records other people rely on); a migration to make those keys nullable (not worth it for this change; revisit if shells pile up).
- Files: `api/Services/AccountDeletionService.cs`, `api/Controllers/AuthController.cs`, `tests/MountedGames.Api.Tests/Auth/AccountDeletionTests.cs`, `web/src/pages/AccountPage.tsx`.

## 2026-10-22: Raw IP addresses are kept for 30 days
- Why: addresses on chat messages and marketplace posts, comments and reports exist so an admin can block an abusive poster. They shouldn't sit in the database for ever.
- Rule: after 30 days (`Privacy:IpRetentionDays`) `IpRetention` replaces each address with `h1:` plus a shortened HMAC-SHA256 of it, keyed from `Privacy:IpHashKey` (or derived from the JWT key). It runs shortly after start-up and every six hours, because the API scales to zero. A hashed address can't be blocked; the block action says so.
- Rejected: plain SHA-256 (the IPv4 space is small enough to reverse); clearing the value (loses the ability to spot a repeat poster inside the same event).
- Files: `api/Services/IpRetention.cs`, `api/Controllers/ChatController.cs`.

## 2026-10-22: Scorer links for volunteers without accounts
- Why: a volunteer scorer shouldn't need an account (or the shared admin key) to score one arena for a day. Accounts stay for people who run the event; links are the narrower, throwaway option decided in `docs/competitive-gaps.md` point 1.
- Rule: anyone who can run a competition (owner, competition admin, site admin) makes a link for one arena with the scorer's name. The link can enter or replace scores for heats in that competition and arena, and read that arena's timetable. Nothing else: no clock, sign-off, reopen, timetable, finals, teams, entries, chat or private data. Anything outside its arena is 404.
- The token is 256 random bits, kept in the URL fragment (`/score#t=…`, so it stays out of server logs and Referer headers) and sent in `X-Scorer-Token`. Only its SHA-256 hash is stored; it's shown once and never logged or returned again. Unknown 404, expired or revoked 410, missing 401, repeated unknown tokens from one address 429.
- Expiry: the end of the day after the competition's end date by default (an event running late still works); the organiser may choose earlier, not later. Revoking is immediate. Every score the link enters is recorded as "Scorer link: {name}" in the score history (`RaceScoreEvent.ActorLabel`).
- Rejected: a short PIN (guessable, so it would need rate limits doing the work of entropy); putting the token in the path or query (logged and sent as Referer); a link that can start and stop the clock (the clock is a staff action).
- Migration: `AddScorerLinks` adds the `ScorerLinks` table and `RaceScoreEvent.ActorLabel`; additive only.
- Files: `api/Entities/ScorerLink.cs`, `api/Auth/ScorerLinkAccess.cs`, `api/Controllers/ScorerLinksController.cs`, `api/Controllers/ScorerController.cs`, `web/src/pages/ScorerPage.tsx`, `web/src/pages/competition/ScorerLinksCard.tsx`, `web/src/offline/scorerLink.ts`.

## 2026-10-16: Admins approve new trainers
- Why: trainer signup was open to anyone, and trainers can create public competitions and (with live video) broadcast on them.

## 2026-10-16: Live video through the Cloudflare Realtime SFU
- Why: organisers want to broadcast the arena from a phone to 50–200 spectators with under a second of delay; a phone can't upload a copy per viewer.
- Rule: the API alone talks to Cloudflare (`Streaming:Cloudflare:*`), so no browser ever sees the app token or SFU session ids. Broadcasters (admins, and the trainer who created the competition, via `[CompetitionAccess]`) publish over HTTP in two phases (`POST` then `/ready`); spectators negotiate anonymously over the live hub (`WatchStream`/`AnswerStream`) with opaque watch ids, a global session cap, a token bucket and a per-connection limit.
- Overlays (now-racing strip, announcements, Back soon, viewer count, and later score cards and admin banners) are drawn by the app over the video, never burned into it.
- Rejected: Cloudflare Stream WHIP/WHEP (about $1 per 1,000 viewer-minutes and no viewer counts); a phone-to-phone mesh over SignalR (a phone's upload can't serve every viewer); YouTube Live (can't broadcast from our site); LiveKit Cloud (free plan too small for 200 viewers).
- Not yet: recording and replays (the client's decision), Nest or RTMP cameras, a player that floats across pages.

## 2026-10-25: Duplicate and starting points copy the set-up, never the entrants
- Why: "Duplicate for next year" used to copy teams, heats and lanes, so an organiser had to delete last year's entrants before starting. The new-competition wizard also needs "Copy a past competition" without needing the old event to still exist.
- Rule: one `CompetitionSetup` (`Services/EventTools/CompetitionSetup.cs`) is read from a competition and applied to a new one, by both the clone and saved starting points. It holds sections (format, scoring settings, finalists, price, cap), sessions (the timetable plan with start times relative to the event start, lanes, minutes, rotation, planned race lists), hatbands, terms, the dec form setup and payment details. A session with no planned list takes its race list from its first heat. A finals session keeps its empty lettered final heats (label, order, timing, race names, no teams) so "Populate from standings" still works in the new event. It holds no teams, heats, results, entries, signups or payments, and no personal data. The live `[paused:…]` and `[shift:…]` notes are dropped.
- A starting point (`StartingPoint`) is that set-up under a name, private to the organiser who saved it (admins see and manage all; anyone else gets 404). Up to 50 each. Deleting an account deletes its starting points.
- The new event is owned by whoever creates it. The dec form's payout club is pinned to the creator's club, or cleared when they have none, as for any new competition; the source event's club is never kept.
- Starting dates: a new competition needs a start date, so creating from a starting point requires one (the end date is optional). Session times are shifted from it.
- Not copied: organiser name, stream URL, sponsors, scorer links, the entries-close dates, commerce settings.
- Files: `api/Services/EventTools/`, `api/Controllers/StartingPointsController.cs`, `api/Entities/StartingPoint.cs`, migration `AddStartingPoints`.
## 2026-10-25: Final scoring options (standard format)
- Why: organisers run the final differently: some add the heats' points into it, some score it fresh, some double it, and some have no final at all.
- Switches, per section, standard format only (`UsesRaceFinals` false). Heat, heat, final has no separate final: it stores the switches, refuses to be given a non-default one, and ignores them everywhere.
  - `HasFinal` (default true): the section may have a finals session. Off: creating, scaffolding or populating finals for it answers 409. It can't be turned off once a lettered final heat exists.
  - `CarryPointsIntoFinal` (default false for new sections): see below. Can be changed at any time, because it only changes how standings add up.
  - `DoublePointsInFinal` (default false): the points a place earns in a lettered final ("A Final") are doubled **when the race is saved**, inside `ScoringService`, so every total, export and standings reader sees the doubled figure. A referee's `[pts:N]` is the figure they typed and is not doubled; `[adj:±N]` moves the doubled placing points. Whole or half points stay whole or half. Saved points are not recalculated, so the setting can't be changed once a final race has scored (409).
- Standings (`StandingsService`, and the same `SectionScoring.Total` in the printed results and the season publication): the final a team is in still decides its place before points do. Within it:
  - Carry **on**: a finalist's total is all its points, earlier and final (plus any tack check bonus). This is how every section behaved before the switch.
  - Carry **off**: a finalist's total is its final's points alone, and teams level on those go through the section's tie-break using only their final results (countback on final placings, or the last final race), not the earlier sessions. A team that missed the final keeps its own total and sits after the finalists, as before. The tack check bonus counts only when points carry, because it belongs to the event as a whole.
  - `StandingRow.FinalPoints` and `EarlierPoints` give the split for finalists (null otherwise); `TotalPoints` is what the row is ranked on.
- Finals seeding (`RankForFinalsAsync`, `FinalsBoundary`) is unchanged: it ranks on all points scored before the final.
- The organiser's tie order (`PUT /finals/tie-order`) now takes its "level on points" totals from the standings, so a tie inside a no-carry final is ordered on the final's points.
- Existing sections are migrated with `CarryPointsIntoFinal = true` so published standings don't change. The entity default is off, but `CreateSectionRequest` defaults `CarryPointsIntoFinal` to **true** for now (today's behaviour) until the Sections page gets the switch, which the web agent adds after merge; then the request default can become off. Duplicating an event copies the three switches. Creating finals for every age group at once (no section id) leaves out sections with no final.
- Not changed: the live "needed to win" projections on the toplist page still add a team's earlier session points to what it can still score (`web/src/lib/toplist.ts`); they start from the API's total, so they are right for carry and need a follow-up for no-carry finals.
- Files: `api/Services/SectionScoring.cs`, `StandingsService.cs`, `ScoringService.cs`, `api/Controllers/CompetitionsController.cs`, migration `AddFinalScoringOptions`.
## 2026-10-25: Master admin, invitations and blocked accounts
- Why: the redesign gives organisers a way to bring in other organisers and admins, and gives admins a way to stop an abusive account without waiting for someone to spot its address.
- **Master admin** (`Roles.MasterAdmin`): an account holds it **as well as** Admin, so every existing Admin check still passes. Site admins can lock and unlock organiser (approved Trainer) accounts; only a master admin can lock or unlock an Admin. It can't be granted through the API except with the **master admin key**: `POST /api/auth/master-admin { key }` (a signed-in Admin, not the shared admin-key account; auth rate limit; logs the account id only). The host holds only `MasterAdmin__KeyHash`, the SHA-256 in hex of a secret its owner keeps, compared in constant time; without the setting the endpoint answers 404, and a malformed hash stops the API starting outside Development. `Register` ignores the role, `POST /api/admin/users/{id}/roles` refuses it, and only a master admin can change a master admin's roles. The demo admin is seeded as master admin in Development and tests only.
- **Lock** is its own field (`AppUser.LockedAt`), not Identity lockout: the existing admin "unlock" clears Identity lockout, so using it would let any admin undo a lock, and an emptied (deleted) account already uses the far-future lockout. A locked account can't sign in (403 `account_stopped`, only after the right password, so a lock isn't revealed to a guesser), and its tokens stop working through `LiveAccounts`. Refused: yourself, a master admin, the shared admin-key account, and anyone who is neither Admin nor Trainer. Endpoints (admins; locking an Admin needs a master admin): `POST/DELETE /api/admin/users/{id}/account-lock`, `GET /api/admin/staff-accounts`.
- **Block** (`AppUser.BlockedAt`, `BlockReason`; any admin; `POST/DELETE /api/admin/users/{id}/block`): same effect as a lock, so the person can't sign in, enter competitions or post in chat (every one of those needs a valid token). The reason is only in `GET /api/admin/blocked-users`. Only a master admin can block or unblock an Admin account; nobody can block themselves, a master admin or the shared account.
- **Networks.** Sign-in, sign-up and invitation acceptance record the visitor's address in `AccountIps` as a keyed hash only (the same HMAC as IP retention), the latest 20 per account. Blocking an account adds those hashes, plus the hashed addresses on its recent chat and marketplace posts, to `IpBlocks` with `BlockedAccountUserId` set. Every IP block check (`IpBlocking.IsIpBlockedAsync`) matches the raw address or its hash. These rows stay out of the IP list and go when the account is unblocked (a network another blocked account also used stays blocked for that one). A network that five or more other accounts have used is treated as shared (a venue's wifi) and is not blocked.
- **Invitations** (`AccountInvite`; admins; `POST/GET /api/admin/invites`, `POST .../{id}/resend`, `DELETE .../{id}`, and anonymous `POST /api/auth/invites/lookup` and `/accept`, rate limited as sign-in). A 256-bit token goes in the emailed link's fragment (`/invite#t=…`, so it isn't logged); only its SHA-256 is stored. A link lasts 7 days and works once; resending issues a new token (the old one stops), at most once a minute and ten times. Accepting asks for a name and a password only, creates the account with a confirmed email (the link proved the mailbox) as Trainer (organiser) or Admin (site admin), and signs the person in. An address that already has an account can't be invited. The email is sent inline with the usual short timeout and the admin sees whether it went (`emailStatus`).
- **Closing the ways round a lock or block.** Only a master admin grants or revokes the Admin role (role endpoint and `/register`); a locked or blocked account's roles are frozen (409); `LockedByMaster` and `BlockedByMaster` record who acted, so only a master admin lifts a master admin's lock or block. Admin-key sign-in is refused from a blocked network and for an email belonging to a locked or blocked account. **Anyone who knows `Admin__Key` can still sign in as the shared account and mint a new Admin account, so locking an admin who knows the key means rotating `Admin__Key`.** Networks added because of an account block apply to sign-in, sign-up, entries and chat but never to public pages (`includeAccountBlocks: false` in `PublicRead`); only addresses an admin typed apply there. Adding them is one insert-if-absent statement, so two blocks racing for a network can't fail. Hashes are keyed from `Privacy:IpHashKey`, falling back to `Jwt:Key` (a startup warning outside Development when it isn't set).
- Tokens live for 24 hours and `LiveAccounts` caches for 60 seconds, so on another API instance a lock or block can take up to a minute to bite; on the instance that handled it, it is immediate.
- Files: `api/Services/Accounts/`, `api/Controllers/AccountAccessController.cs`, `AccountInvitesController.cs`, `api/Auth/LiveAccounts.cs`, `Roles.cs`, migration `AddAdminAccounts`.
## 2026-10-25: Custom emails to an audience, sent a batch at a time
- Why: admins want to write to the news list, to trainers, or to organisers and admins, with a picture, a button or a competition card, without a mailing tool.
- Audiences (`CustomEmailAudiences`, one place, so the count an admin sees is the list that is mailed): **News** is everyone still opted in (`EmailOptIn`, one row per address); **Trainers** and **Organisers and admins** are accounts holding the role with a **confirmed** address that is a real mailbox (made-up `@...mg.local` username addresses are skipped). Duplicates are removed ignoring case.
- Blocks, in order: text (plain; blank lines make paragraphs; nothing typed is ever read as markup, so it can't become HTML), picture, button (label up to 60 characters and an https link, no credentials), competition card (name, dates, venue and an Enter link, read once when the email is made). At most 30 blocks and 30,000 characters of text; the subject is one line of up to 150 characters.
- Pictures are uploaded as the raw image body (`POST /api/admin/custom-email-images`), png, jpeg or webp by magic bytes against the declared type, never SVG, 500 KB at most (sponsor logos are 200 KB; an email picture needs more room). Stored in the row and served anonymously at `/api/email-images/{guid}`: a mail app has to fetch it, the id is a random GUID so it can't be guessed, and it is served `nosniff` with the type judged from its bytes, and limited per address by the public-read limiter (a mail app's image proxy shares addresses, so raise `RateLimits:PublicReadsPerMinute` if a big send's pictures start failing). Pictures no email ever used are deleted after two days.
- **Sending with no queue** (the API scales to zero, so nothing may depend on a process staying up): `POST /api/admin/custom-emails` freezes the rendered email and the recipient list in the database and sends nothing; the admin's page then calls `POST .../{id}/send-batch` until `remaining` is 0. A batch is 10 people (`Email:CustomBatchSize`) one after another (the provider limits requests a second) and stops after 20 seconds (`Email:CustomBatchSeconds`) once it has handled at least one person, handing the rest back. Each person is claimed before they are mailed, so two browsers or instances can't both take them; a claim older than two minutes is treated as abandoned and taken again; every message carries the idempotency key `custom-email-{id}-{recipient}` so the provider drops a repeat after a crash. A closed tab only pauses the send; the same call resumes it, from any instance. Cancel deletes what is left.
- **Addresses are kept only while needed.** A recipient row is deleted the moment the provider accepts the message (the email keeps only counts: total, sent, failed, skipped). Failed rows stay for a week so they can be retried (`retry-failed`), then are dropped. The frozen text and HTML are stored with the email so it can be shown later; they hold no recipient address. Logs carry ids and counts only, never an address, subject, body or link.
- **Confirm in the request**: `confirm: true` and `expectedRecipients` (the number the admin saw). If the list has changed the answer is a 409 with the new number and nothing is sent. Sending needs email switched on (409 otherwise). At most 10 custom emails a day.
- **Unsubscribe** (news audience only): each message has its own link and RFC 8058 one-click headers: `List-Unsubscribe` pointing at the signed `POST /api/email/unsubscribe-one-click?token=` (plus the page link) and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. The token stored with a consent is shown once and only its hash is kept, so these links are signed instead (`n1.{consent id}.{HMAC}`, `EmailUnsubscribeTokens`): no address in them, nothing stored, any instance can verify them, and they never expire. `POST /api/email/unsubscribe` accepts both kinds. Someone who unsubscribes mid-send is skipped.
- A test send goes only to the signed-in admin's own address, marked `[Test]`; a preview and a test touch no list.
- Locked and blocked accounts, the shared `admin@mg.local` account and any `@mg.local` or `.mg.local` address are left out of every audience.
- Files: `api/Services/Email/CustomEmailService.cs`, `CustomEmailRenderer.cs`, `api/Controllers/CustomEmailsController.cs`, `api/Entities/CustomEmail.cs`, migration `AddCustomEmails`.
